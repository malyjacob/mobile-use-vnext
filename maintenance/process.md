# 工程流程：分诊 → 分析 → 提案（可选）→ 执行 → 归档

状态：2026-11-20。本页只约束工作方式，不描述任何产品行为。正式架构与契约以本仓库的
[正式文档](../docs/) 为准；本页与提案、决策、验证记录同属 `maintenance/`。
本仓库独立维护设计与实现，不把其他项目仓库作为设计权威或实施前置，也不要求读取、修改、
提交或推送其他项目仓库。构建使用本仓库源码、已声明的版本依赖和固定制品，不要求旧项目的
源码目录、分支、代码或规范存在，也不操作旧项目。规范冲突与变更在本仓库内按以下流程处理。

流程的价值在出口条件，不在步骤数量。**能跳的跳，不能跳的别省**：

```text
问题（现象，或可观测的代价）
   │
   ├─ 分诊：这是缺陷还是取舍？（§1）
   │
   ├─ 缺陷 → 分析（归因）              不可跳过
   │           复现用例先红 + 根因 file:line + 同类核查
   │             └─ 根因落在现行规范上 → 转取舍
   │
   └─ 取舍 → 讨论（路线对比）→ 提案     讨论与提案可跳过（§2）
   │
   ▼
执行：实现 + 测试 + 文档审计           不可跳过
   │ 实现提交
   ▼
归档：有提案 → 提案归档；无提案 → 验证记录（§7）
```

提案格式见 [proposals/template.md](proposals/template.md)；已实现的提案在
[proposals/implemented/](proposals/implemented/) 下，文件名保持不变。

---

## 1. 分诊：先判断这是哪一类

判据只有一句：**问题能不能用“现行规范说得对，实现走偏了”解释？** 能，就是缺陷；
不能，就是取舍。

| 输入 | 判据 | 走向 |
| --- | --- | --- |
| 缺陷报告（issue、报错、异常现象） | 行为与现行契约或架构不一致 | 归因（§3）→ 直接修 → 验证记录 |
| 缺陷报告 | 现行规范本身导致问题 | 归因（§3）→ 转提案（§5） |
| 需求或设计质疑 | 存在取舍：范围、取值、是否改契约 | 讨论（§4）→ 提案（§5） |
| 需求 | 无取舍、单点、不改公开面 | 直接改，测试与提交信息说明 |
| 规范本身 | — | 直接改 + `decisions.md` |

分诊结论写进第一段提交信息，或写进验证记录的第一节。**分诊错了比不做分诊更糟**：
把设计缺陷当实现缺陷修，会留下“现象消失、根因还在”的第二层问题。

---

## 2. 哪些步骤可以跳过

**只允许跳过“讨论”和“提案”。** 归因、执行、测试与验证记录不可跳过。

| 条件（需同时满足） | 可跳过 | 代价 |
| --- | --- | --- |
| 取舍已被现行规范唯一确定，且不涉及契约、判据、时序 | 讨论 | 决策理由只留在提交信息里 |
| 影响面在单包或单文件族内，无新增公开面 | 讨论 | 同上 |
| 只有一条可行路线，且能用一句话说明其它路线为何不成立 | 讨论 | 同上 |
| 缺陷的根因已由先红的复现用例定位 | 提案 | 没有 §11 式实现记录，只有验证记录 |
| 变更不需要解释“为什么选这条” | 提案 | 同上 |

跳过时必须做的两件事：

1. **在提交信息里声明**“为什么没有讨论 / 没有提案”。跳过的代价是决策理由只剩一句话，
   所以要写清那一句；
2. **超过一屏的取舍一律不跳**。判断标准是“解释清楚需要几段”，不是“代码改了几行”。

**人**可以直接指定跳过；实现 agent 只能按上表跳过，且必须声明。

---

## 3. 分析：缺陷的归因

缺陷不缺方案，缺的是根因。四步，按顺序做：

1. **复现。** 优先写成 Go 测试（放进对应的 `internal/...` 包）；写不成测试的，写成可执行
   的脚本步骤。用例**必须先红**：红不了说明还没走到真实路径，继续取证，不要动实现。
2. **根因。** 定位到 `file:line`，说明为什么会走到这条分支。“改完好了”不是根因。
3. **同类核查。** 同一模式是否还有第二处（同一判据、同一错误分支、同一处假设）。
   这是缺陷与需求的根本差别：需求是加法，缺陷是找同类。
4. **分诊复核。** 如果根因指向现行规范（契约、判据、时序、预算），停下转提案，
   不要在实现里暗改语义。

**出口条件**：复现用例红 + 根因 file:line + 同类核查结论。

---

## 4. 讨论：取舍的路线对比

**不写文件。** 讨论阶段的结论只存在于对话里，避免半成品提案被误读为承诺。

1. **先取证。** 每条关于现有实现的断言都要带 `file:line` 或上游源码位置；“我记得”不是证据。
   一次改动里至少核过：入口在哪、数据从哪来、失败时走哪条分支。
2. **写清代价。** 问题陈述用可观测的事实（哪个错误码、哪一步往返、多花多少毫秒），
   不用“感觉慢”“体验差”。
3. **至少两条路线**，其中一条是“什么都不做”或“最小改动”。每条写代价与失败模式，
   不只写优点。
4. **压缩决策。** 把“必须由人拍板”的问题压到最少（通常是三项：范围、取值、是否暴露给
   调用方），其余自己定，并写进提案 §9.1 供人复核。

**出口条件**：人认可问题定义与路线方向。细节可以再议，但“要不要做、往哪个方向做”
必须一致；否则回到取证。

---

## 5. 提案

1. **落盘**：`maintenance/proposals/<slug>.md`，`slug` 用英文 kebab-case，与主题同名；
   归档后文件名不变。
2. **头部字段固定顺序**：状态、基线提交、适用范围、影响范围、契约是否变化。
3. **状态只有三个值**：`提案，未实现` / `已实现` / `部分实现`。写提案时只能是第一个。
4. **基线提交**是写作时的 `HEAD` 全 hash；文中所有行号、常量、默认值以它为准，并在头部
   声明“代码前进后须重新核对”。
5. **章节顺序见模板**，不要自创结构。两条硬要求：
   - §7 必须写“不能治什么”，且是真实的限制，不是谦辞；
   - §8 必须把单元测试与实机验证分开，并给出可观测的验收指标。
     涉及发布的提案在 §8、§10 写清手机整组部署、最小实机闭环、两个 Windows exe 的替换
     和独立探针，以及依赖方由用户处理的责任边界。具体默认范围见 [AGENTS.md](../AGENTS.md)。
6. **未决项**要么在确认前关闭，要么写明“谁来定、什么时候定”。不允许悬空，也不允许
   把“实施后看着办”写成已定。
7. **缺陷转来的提案**：把复现用例、根因与同类核查直接放进 §1.2 证据链，不重新取证。
8. **草案审阅**：独立、只读的 subagent 按证据、方案边界、验收和发布步骤审阅草案，返回文件行
   与建议。实现 agent 逐项处理并就重大修订请求复检，收敛后将草案及结论一并呈交用户。
   评审期间保留送审稿，等待结论。正式文档审计在实现阶段按第 15 条另行执行。

**出口条件**：人明确确认（例如“就按这个落”）。此后提案内容即实现契约；改判据、改契约、
改时序都要回到本阶段修订并重新确认。

---

## 6. 执行

涉及退休交接时，按当前逻辑工作与有限交接检查归属，不将旧物理未知当作新准入条件。验证范围服从用户当次约束，覆盖真实变更路径和发布部署必要检查，不扩展无关设备或功能矩阵。

涉及发布时，按提案完成核验后的手机整组覆盖部署、变更所涉最小实机闭环、主机工具替换，
并以新产物分别验证独立 stdio 和手机 HTTP MCP。记录实际产物、磁盘镜像和独立进程的证据。
依赖 Agent 的配置、托管进程和重连默认由用户处理。其状态不作为独立探针验证或本仓库交付门禁。

顺序固定，不跳步：

```text
读目标代码 → 最小侵入设计 → 实现 → 单元测试 → 反向对照 → 变更所涉回归
          → 同步 docs → 独立文档审计 → 实现提交
```

- **最小侵入**：优先复用既有参数与既有语义（如按已有的 `phase` 字符串查表），
  不为了新功能扩大公开面。能不新增请求字段就不新增。
- **反向对照**：新加的判据、守卫、幂等类测试，至少有一条要证明“去掉实现会失败”。
  缺陷修复则是“复现用例由红转绿”，并且它留在仓库里作为回归。
- **提案状态此时不动**：实现提交落盘前，提案仍是 `提案，未实现`。
- **偏离**：实现中发现提案写错，允许偏离，但必须同时做三件事：写进 §11.2、写进提交信息、
  更新受影响的 `docs/`。若偏离触及判据、契约或时序，先回到 §5 修订提案并重新确认。
- **`docs/` 只写已具备的行为**：未实现的部分不写进正式文档，留在提案与验证记录里。
  涉及 `docs/` 的变更在提交前通过 AGENTS.md 第 15 条的独立只读文档审计。
- **审计等待**：审计 subagent 运行期间等待其结论，不因“尚未返回”而反复中断或重启；只有
  明确失败、无响应且记录原因时才重新发起。审计期间不改正在审计的 `docs/` 文件。
- **测试通过 ≠ 实机结论**：验证记录里必须分开写“已实现 / 已单测 / 已实测”。

**出口条件**：实现提交存在、变更所涉测试及发布必要回归通过、`docs/` 审计 clean（若改了 `docs/`）。

## 7. 归档

### 7.1 有提案：先提交实现，再归档

**先提交实现，再归档。** 两个原因：

- 归档头要写实现提交的 hash，而 hash 只在提交后存在。先归档再用 amend 补，会让提案在
  实现提交里指向一个不存在的对象；
- 文档审计门禁只覆盖实现提交。归档提交不改 `docs/`，因此不必再跑一次审计。

若实现跨多次提交，归档放在**最后一次**之后，头部写最后一个实现提交，§11.1 列出全部提交。

归档动作，按顺序做完再提交：

1. 移动到 `maintenance/proposals/implemented/`，文件名不变；
2. **重写仓库相对链接**：目录深了一层，仓库相对链接各加一级（例如 `../../` 变
   `../../../`）；移动后跑一次链接目标存在性检查，断链不算完成；
3. 头部改为 `状态：已实现（实现提交 <hash>，<日期>）`，并加一行实现与验证记录的链接；
4. 追加 **§11 实现结果**，两张表：
   - §11.1 已落地：提案条目 → 代码落点（文件与函数级）；
   - §11.2 与提案不同或未执行：逐条写结论与**理由**。未执行就写“未执行”+原因，
     不写“后续补”；
5. 写 `maintenance/verification/<同名>.md`：实现提交、环境、实际执行的命令、真实结果、
   用例与证明窗口、未执行项与原因；开头声明是否涉及实机；
6. 更新 `maintenance/status.md`：只有“已实测 / 未验证”的结论变化时才改一行；
7. 单独提交，提交信息写清“归档了哪份提案、§11 记录了什么、哪些没做”。

**部分实现**：代码未全部落地时，头部写 `部分实现` 并在第一行点明缺口；§11.1 只列已落地
部分，§11.2 逐条写未落地项与理由；`docs/` 只写已落地部分。

### 7.2 无提案：写验证记录

缺陷修复与跳过提案的小改动不建提案，但**必须有记录**，否则下次同类问题要重新取证。

写 `maintenance/verification/<topic>.md`，六节：

1. 现象与触发条件（用户看到什么，哪个错误码）；
2. 复现用例位置（测试函数或脚本步骤），以及修复前它是红的；
3. 根因（`file:line` + 为什么走到这条分支）；
4. 修复提交与改动的边界；
5. 同类核查结论（有或没有，怎么确认的）；
6. 未覆盖项与原因（不写“后续补”）。

记录可以与修复同一提交：此时第 4 节写“修复提交：本记录所在提交”，并在提交信息里写
根因与复现用例路径。若修复跨多次提交，记录放最后一次。

## 8. 提交切分

| 情形 | 提交 | 门禁 |
| --- | --- | --- |
| 有提案（实现 + `docs/`） | 1：实现 + `docs/`；2：提案归档 + 验证记录 + `status.md` | 提交 1 必须有独立只读审计的 clean 结论 |
| 无提案的缺陷修复 | 单提交：修复 + 验证记录（+ `docs/` 若行为与文档不一致） | 涉及 `docs/` 时同样要审计 |
| 规范变更 | 单提交：规范文件 + `decisions.md` | 不改 `docs/`，不触发审计 |

提交信息写“改了什么、为什么这么改、故意没做什么”。跳过了讨论或提案的，在提交信息里
写明理由。

## 9. 角色

| 角色 | 做什么 | 不能做什么 |
| --- | --- | --- |
| 人 | 确认问题、拍板决策、确认提案、接受归档、指定跳过 | — |
| 实现 agent | 取证、归因、写提案、实现、自检、写记录 | 自我批准提案、自我审计、把未执行的验证写成已验证、擅自跳过提案 |
| 提案审阅 subagent | 只读审阅草案和重大修订，返回发现项与建议 | 修改草案、替用户确认提案 |
| 审计 subagent | 只读审核 `docs/`，返回 `file:line` 与最小修正 | 实现、改文件、承担设计决策 |

审计 subagent 运行期间，实现 agent 应等待其结论；不得把“尚未返回”判为卡住而反复中断或
重启。只有明确失败、无响应且记录了原因时才重新发起，并在提交说明中注明。

## 10. 常见错误（都是真实发生过的）

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 凭记忆断言实现（记错了输入走哪条通道） | 提案证据链错误，返工 | 每条断言回代码取证据；两条通路就写两条独立证据链 |
| 面对可用性问题先加参数（把等待时长交给调用方） | 契约变复杂，调用方要为服务端策略负责 | 先问“服务端能否自己判定”；能则不新增字段 |
| 提案写“维持现有语义”但没核对基线 | 实现时才发现响应分支变了 | 提案里把“会变的响应字段与分支”逐行对代码 |
| `docs/` 里顺手写一句行为判断 | 文档漂移，审计才发现 | 每句行为断言都要能指到代码行；指不到就不写 |
| 先改提案再提交实现 | 归档头指向不存在的 hash | 先实现提交，拿到 hash 再归档 |
| 移动提案后忘记改相对链接 | 断链 | 移动后跑链接存在性检查 |
| 把单测通过写成实机结论 | 证据分层失效 | 记录里分开写已实现 / 已单测 / 已实测 |
| 复现用例没先红就修 | 修完无法证明修的是这个现象 | 用例先红，再动实现 |
| 只修报告的那一条路径，不查同类 | 同一根因在别处复发 | 归因时做同类核查 |
| 用加超时、加重试、吞错误让现象消失 | 根因还在，故障变成静默 | 归因到 `file:line` 再决定改什么 |
| 跳过了讨论/提案却没在提交信息里声明 | 三个月后无法解释为什么这么做 | 跳过的步骤必须在提交信息里写明理由 |
| 审计 subagent 尚未返回就反复中断/重启 | 审计无结论、时间浪费、工作区状态混乱 | 等它返回；只有明确失败/超时且记录原因时才重启，重启后说明原因 |
