# 工程流程：讨论分析 → 确认提案 → 执行 → 登记归档

状态：2026-11-09。本页只约束工作方式，不描述任何产品行为。正式架构与契约在 `docs/`；
本页与提案、决策、验证记录同属 `maintenance/`。

一次改动的生命周期是四段，每段都有出口条件，没达到就不进入下一段：

```text
问题（可观测的代价）
   ↓ 讨论分析：取证、路线对比、待拍板清单
确认提案（落盘到 maintenance/proposals/）
   ↓ 执行：实现 + 测试 + 同步 docs + 文档审计
实现提交
   ↓ 登记归档：移动提案、补 §11、写验证记录
归档提交
```

提案格式见 [proposals/template.md](proposals/template.md)；已实现的提案在
[proposals/implemented/](proposals/implemented/) 下，文件名保持不变。

---

## 1. 判断是否需要提案

判据只有一句：**三个月后有人问“为什么是这样”，只靠代码、测试和提交信息能不能回答？**
不能，就需要提案。

需要提案：

| 变更类型 | 例 |
| --- | --- |
| 改变外部可观察语义 | 后置观察从“派发后立即”改成“树收敛后” |
| 引入新的判据、策略或预算 | 收敛判据、静默窗口、重试上限 |
| 跨多个包，或改变包间职责 | 把身份函数从 `act` 提到共享层 |
| 多条路线都可行，选错代价在数月后才显现 | 本地判定 / 调用方传参 / 事件驱动 |
| 改契约 | 新增或删除请求字段、响应字段、错误码 |

不需要提案：

| 变更类型 | 走什么 |
| --- | --- |
| 局部缺陷修复（根因不是设计错误） | 直接修并提交 |
| 纯测试、注释、链接、措辞修正 | 直接改 |
| 跟随既有规范的机械改动 | 直接改 |
| 流程或规范本身的变更 | 直接改 `AGENTS.md` 与 `maintenance/process.md`，并记入 `decisions.md` |

例外：**人**可以直接指定跳过提案（例如紧急修复，或已在对话里充分讨论过的小改动）。
跳过时在 `decisions.md` 记一条，写明跳过理由与替代的评审方式；实现 agent 不得自行决定
跳过。

---

## 2. 阶段一：讨论分析

**不写文件。** 讨论阶段的结论只存在于对话里，避免半成品提案被误读为承诺。

1. **先取证。** 每条关于现有实现的断言都要带 `file:line` 或上游源码位置；“我记得”不是证据。
   一次改动里至少核过：入口在哪、数据从哪来、失败时走哪条分支。
2. **写清代价。** 问题陈述用可观测的事实（哪个错误码、哪一步往返、多花多少毫秒），
   不用“感觉慢”“体验差”。
3. **至少两条路线**，其中一条是“什么都不做”或“最小改动”。每条写代价与失败模式，
   不只写优点。
4. **压缩决策。** 把“必须由人拍板”的问题压到最少（通常是三项：范围、取值、是否暴露给
   调用方），其余自己定，并写进提案 §9.1 供人复核。

**出口条件**：人认可问题定义与路线方向。细节可以再议，但“要不要做、往哪个方向做”
必须一致；否则回到取证。

---

## 3. 阶段二：确认提案

1. **落盘**：`maintenance/proposals/<slug>.md`，`slug` 用英文 kebab-case，与主题同名；
   归档后文件名不变。
2. **头部字段固定顺序**：状态、基线提交、适用范围、影响范围、契约是否变化。
3. **状态只有三个值**：`提案，未实现` / `已实现` / `部分实现`。写提案时只能是第一个。
4. **基线提交**是写作时的 `HEAD` 全 hash；文中所有行号、常量、默认值以它为准，并在头部
   声明“代码前进后须重新核对”。
5. **章节顺序见模板**，不要自创结构。两条硬要求：
   - §7 必须写“不能治什么”，且是真实的限制，不是谦辞；
   - §8 必须把单元测试与实机验证分开，并给出可观测的验收指标。
6. **未决项**要么在确认前关闭，要么写明“谁来定、什么时候定”。不允许悬空，也不允许
   把“实施后看着办”写成已定。

**出口条件**：人明确确认（例如“就按这个落”）。此后提案内容即实现契约；改判据、改契约、
改时序都要回到本阶段修订并重新确认。

---

## 4. 阶段三：执行

顺序固定，不跳步：

```text
读目标代码 → 最小侵入设计 → 实现 → 单元测试 → 反向对照 → 全量回归
          → 同步 docs → 独立文档审计 → 实现提交
```

- **最小侵入**：优先复用既有参数与既有语义（如按已有的 `phase` 字符串查表），
  不为了新功能扩大公开面。能不新增请求字段就不新增。
- **反向对照**：新加的判据、守卫、幂等类测试，至少有一条要证明“去掉实现会失败”。
  只会变绿的测试不算证据。
- **提案状态此时不动**：实现提交落盘前，提案仍是 `提案，未实现`。
- **偏离**：实现中发现提案写错，允许偏离，但必须同时做三件事：写进 §11.2、写进提交信息、
  更新受影响的 `docs/`。若偏离触及判据、契约或时序，先回到阶段二修订提案并重新确认。
- **`docs/` 只写已具备的行为**：未实现的部分不写进正式文档，留在提案与验证记录里。
  涉及 `docs/` 的变更在提交前通过 AGENTS.md 第 15 条的独立只读文档审计。
- **测试通过 ≠ 实机结论**：验证记录里必须分开写“已实现 / 已单测 / 已实测”。

**出口条件**：实现提交存在、全量测试通过、`docs/` 审计 clean（若改了 `docs/`）。

---

## 5. 阶段四：登记归档

**先提交实现，再归档。** 两个原因：

- 归档头要写实现提交的 hash，而 hash 只在提交后存在。先归档再用 amend 补，会让提案在
  实现提交里指向一个不存在的对象；
- 文档审计门禁只覆盖实现提交。归档提交不改 `docs/`，因此不必再跑一次审计。

若实现跨多次提交，归档放在**最后一次**之后，头部写最后一个实现提交，§11.1 列出全部提交。

归档动作，按顺序做完再提交：

1. 移动到 `maintenance/proposals/implemented/`，文件名不变；
2. **重写仓库相对链接**：目录深了一层，仓库相对链接各加一级（例如 `../../` 变
   `../../../`）；移动后跑一次链接目标存在性检查，断链不算完成；
3. 头部改为 `状态：已实现（实现提交 <hash>，<日期>）`，并加一行实现与验证记录的链接；
4. 追加 **§11 实现结果**，两张表：
   - §11.1 已落地：提案条目 → 代码落点（文件与函数级）；
   - §11.2 与提案不同或未执行：逐条写结论与**理由**。未执行就写“未执行”+原因，
     不写“后续补”；
5. 写 `maintenance/verification/<同名>.md`：实现提交、环境、实际执行的命令、真实结果、
   用例与证明窗口、未执行项与原因；开头声明是否涉及实机；
6. 更新 `maintenance/status.md`：只有“已实测 / 未验证”的结论变化时才改一行；
7. 单独提交，提交信息写清“归档了哪份提案、§11 记录了什么、哪些没做”。

**部分实现**：代码未全部落地时，头部写 `部分实现` 并在第一行点明缺口；§11.1 只列已落地
部分，§11.2 逐条写未落地项与理由；`docs/` 只写已落地部分。

**出口条件**：提案在 `implemented/` 下、链接全部可解析、验证记录与 `status.md` 一致、
工作区干净。

## 6. 提交切分

| 提交 | 内容 | 门禁 |
| --- | --- | --- |
| 1 | 实现 + `docs/` 同步 | 涉及 `docs/` 时必须有独立只读审计的 clean 结论 |
| 2 | 提案归档 + 验证记录 + `status.md` | 不改 `docs/`，不触发审计 |

提交信息写“改了什么、为什么这么改、故意没做什么”。多提交变体见上一节。

---

## 7. 角色

| 角色 | 做什么 | 不能做什么 |
| --- | --- | --- |
| 人 | 确认问题、拍板决策、确认提案、接受归档 | — |
| 实现 agent | 取证、写提案、实现、自检、写记录 | 自我批准提案、自我审计、把未执行的验证写成已验证 |
| 审计 subagent | 只读审核 `docs/`，返回 `file:line` 与最小修正 | 实现、改文件、承担设计决策 |

---

## 8. 常见错误（都是真实发生过的）

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 凭记忆断言实现（记错了输入走哪条通道） | 提案证据链错误，返工 | 每条断言回代码取证据；两条通路就写两条独立证据链 |
| 面对可用性问题先加参数（把等待时长交给调用方） | 契约变复杂，调用方要为服务端策略负责 | 先问“服务端能否自己判定”；能则不新增字段 |
| 提案写“维持现有语义”但没核对基线 | 实现时才发现响应分支变了 | 提案里把“会变的响应字段与分支”逐行对代码 |
| `docs/` 里顺手写一句行为判断 | 文档漂移，审计才发现 | 每句行为断言都要能指到代码行；指不到就不写 |
| 先改提案再提交实现 | 归档头指向不存在的 hash | 先实现提交，拿到 hash 再归档 |
| 移动提案后忘记改相对链接 | 断链 | 移动后跑链接存在性检查 |
| 把单测通过写成实机结论 | 证据分层失效 | 记录里分开写已实现 / 已单测 / 已实测 |
