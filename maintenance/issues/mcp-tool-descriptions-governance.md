# Issue：MCP 服务工具说明系统的现状评估与优化治理指导意见

状态：治理指导意见（待分诊与路线确认）。  
日期：2026-11-18。  
范围：MCP 服务入口发布的全局指令、工具目录描述、入参 Schema、协议注解及配套规范文档。

---

## 1. 背景与目标

本仓库 MCP 服务向调用方 Agent 公开了固定 13 个工具与整套结果/树语法规范。随着协议演进（如统一 `reference`、复合 `text`、受控 `scroll`、`snap` 等能力陆续合入），当前工具说明系统已具备极高的工程严谨度，但也积累了一定的上下文负担、表达冗余与跨工具策略不对称问题。

本文旨在不陷入具体代码实现细节的前提下，客观梳理现有设计的优势与痛点，明确后续作为项目维护者的总体治理方向与实施节奏。

---

## 2. 现有设计的优秀之处

在进行任何优化前，必须先确认当前说明系统已经建立起来的几道关键防线——这些设计在同类 MCP 服务中属于高水准实践，后续治理必须完整保留：

1. **单一事实源与防漂移门禁成熟**
   - 全局说明与工具目录集中维护、显式定义，不依赖结构体标签自动推导，从源头上避免了隐式默认值或字段语义失真。
   - 引入了规范化工具目录指纹，并将静态基线校验、发布清单核验与活体探针逐字比对串联成闭环，确保“源码说明—发布产物—线上服务—正式文档”四者严格一致。
2. **明确站在“调用方视角”划定表达边界**
   - 文案内容经过严格约束：清晰告知调用方意图、参数边界、副作用与恢复路径，同时刻意隔离了内部实现细节（如节点落点计算算法、内部存储或账本机制）与已废弃的旧别名，防止模型被内部术语误导。
3. **静态契约与运行时反馈形成闭环**
   - 工具说明不试图把所有异常分支硬塞进静态提示词，而是与运行时的结构化错误详情和恢复建议相互配合——静态层面教导“如何看懂状态与恢复字段”，动态层面在每次失败时给出下一步动作路标。
4. **针对 Agent 常见幻觉做了前置防呆与宿主兜底**
   - 对高频易混概念（如原始手势与受控滚动的界限、状态字段的省略与置空差异、分支参数的互斥规则等）均设置了清晰边界；并考虑到部分 MCP 宿主可能忽略服务级指令，在入口工具描述中保留了轻量降级提示。

---

## 3. 现有的弊端与不足之处

尽管工程防线很稳固，但从“大模型消费效率、客户端协议兼容性与长期可维护性”来看，当前工具说明系统存在以下几类突出问题：

### 3.1 上下文体积偏重，长段落信息密度过高
- 虽然此前已将树语法图例从各工具中抽离到全局指令，但整个发现阶段（全局指令 + 13 个工具目录与 Schema）的总字节预算上限仍维持在约 36 KB 量级，初始上下文开销较重。
- 特别是核心工具（如操作类、应用生命周期管理类）的描述文本和全局指令，多以高度浓缩的连续长句堆叠，缺乏分点或分段呼吸感。对于推理能力极强的大模型尚可消化，但在长会话、多工具并存或上下文受限的模型上，容易引发局部规则遗漏或注意力稀释。

### 3.2 三层说明职责边界不够锐利，存在跨层复述
- 当前说明分布在**服务级全局指令、工具级描述、参数字段描述**三个层级。由于各阶段迭代叠加，部分重要规则（如默认行为开关、等待超时预留、部分错误恢复动作）同时在两到三层中反复出现。
- 这种冗余虽然带来了一定容错性，但也直接推高了总 Token 占用，并增加了后续修改契约时“漏改其中一层”的维护风险。

### 3.3 入参 Schema 的约束风格在工具间不统一
- 为了兼容对复杂 JSON Schema 支持不佳的宿主与模型适配器，应用生命周期工具刻意采用“完全扁平结构”，禁止一切条件组合关键字，把分支互斥完全留给服务端严格校验。
- 然而，同目录的交互操作工具与树补看工具却仍使用了 `oneOf`、`not` 等条件组合关键字。这种“同一服务内采用两套 Schema 兼容性假设”的做法，可能导致不同宿主或模型在工具注册解析阶段出现不一致行为（有的能正常校验，有的直接报错或静默丢弃约束）。

### 3.4 MCP 协议层注解（`Annotations`）发布存在明显不对称
- 从工具本质与文字描述看，`status`、`inspect`、`diagnose` 与 `snap` 均属于只读查询类能力，但在协议暴露层面，当前仅有 `snap` 发布了只读注解（`readOnlyHint`），其余三个只读工具均未发布。
- 同时，对具有明显状态破坏性或高风险的操作（如结束会话、终止进程、执行命令等）也未配合相应的标准提示注解。对于依赖 MCP 标准注解来做安全确认、只读徽章展示或自动放行策略的宿主而言，协议层语义与实际行为存在割裂。

### 3.5 缺乏“调用误用率”驱动的文案度量机制，且存在外围口径漂移
- 现有测试与探针重在检验“说明有没有漏字、指纹有没有对上、是否泄露内部词”，却缺少“Agent 在实际使用中究竟哪条规则最容易理解错”的反向反馈通道。哪些参数最常触发参数拒绝，哪些错误最常导致错误重试，目前缺少与说明优化联动的定期复盘机制。
- 此外，部分外围工程约束文档中仍残留旧阶段描述（例如仍将公开工具目录记为 12 个而非当前的 13 个），虽然不影响线上运行，但容易对新接手维护者造成认知偏差。

### 3.6 生态扩展维度上的潜在局限
- 当前所有说明与字段解释均为纯中文长文本，也未提供响应结构说明（`outputSchema`）或按需获取的分层补充指引。如果未来需要接入对中文语义相对薄弱的外部模型生态，或面对极限上下文窗口环境，全量一次性注入的纯中文文案将缺乏弹性。

## 4. 总体优化治理思路与方案

治理的总基调是**“增量收敛、数据驱动、守住基线、不做过度设计”**，围绕以下五个方向推进：

### 4.1 明确三层说明的唯一职责，推行“结构化瘦身”
对现有全部文案做一次职责清分，原则上每一类信息只在一个最合适的层级出现：
- **服务级全局指令**：只保留跨工具共享的状态机与语法规范（会话生命周期、标识与租期规则、统一恢复分类、结果与树文本图例），剥离属于单个工具的细枝末节。
- **工具级描述**：采用清晰的短句分段/分点排版，只说清“核心用途、关键副作用、消费前置条件与核心异常出口”，不再整段复述各参数明细。
- **参数字段描述**：只说明“该字段自身的合法形态、默认值与适用分支”。
- **预算精细化**：在保留总字节门禁的基础上，拆出分项观察指标（全局指令 / 工具描述 / Schema 各自占比），防止后续迭代让文案体积无序回弹；仅对确有需要的核心入口保留极简的宿主降级提示。

### 4.2 制定统一的 JSON Schema 兼容基线
- 针对项目实际服务的重点 MCP 宿主与模型适配器建立一套**最小兼容子集清单**，用实测结论而非猜测来决定是否允许 `oneOf`、`not` 等条件关键字。
- 若目标宿主中存在不兼容条件关键字的情况，则将所有工具统一收敛到“扁平 Schema + 清晰字段说明 + 服务端严格校验”的同一口径；若全部兼容，也应将允许使用的关键字白名单固化为统一规范，消除工具间的风格割裂。

### 4.3 完成 MCP 协议注解的正式取舍与对齐
- 将“非 `snap` 的只读工具是否应当发布 `readOnlyHint`”列为一次正式设计分诊：
  - 若经核查确有安全或时序原因必须禁止宿主自动放行或缓存 `status`/`inspect`/`diagnose`，则将原因明确写入架构决策文档，结束模糊状态；
  - 若无实质阻碍，则通过标准提案流程统一补全所有只读工具的 `readOnlyHint`，并评估是否为高风险写/终止类工具补充破坏性提示注解，使协议层元数据与业务语义对齐。

### 4.4 建立“真实误用率 -> 文案迭代”的闭环
- 借助服务和适配器现有的受控运行事件，定期统计真实任务中各工具的静态参数错误与语义拒绝分布，识别出“大模型最容易填错的参数名、最容易误解的默认值、最容易走错的恢复步骤”。
- 将“高频误用点下降”作为修改工具说明的核心验收标准，优先通过更贴近直觉的描述或结构调整来消除歧义，而不是靠不断追加警告句来打补丁。

### 4.5 保持对扩展特性的克制，并清扫外围文档漂移
- 对于英文/多语言化、按需加载提示词（MCP `prompts`/`resources`）及响应 `outputSchema`，在没有明确多语种分发或端侧小模型刚需前，**保持克制、不提前复杂化无状态适配器**，仅在架构上保留文案源可替换的整洁边界即可。
- 顺带核对并修正仓库内非运行态文档（如工程约束中的工具计数等）的滞后表述，确保全仓口径统一。

---

## 5. 建议推进节奏

严格遵循仓库既定的“分诊 → 分析/取舍（必要时提案）→ 执行 → 文档审计 → 清单与探针验证”流程，按优先级分三批推进：

1. **P0（校准与止血）**：完成只读注解与 Schema 兼容子集的正式分诊决策；清理已知外围文档的工具数量等口径漂移。
2. **P1（结构瘦身与可读性提升）**：按三层职责规范重写全局指令与长描述工具文案（重点优化 `act`、`app` 及全局规则的排版与去重），同步刷新目录指纹、正式文档与探针基线，并通过文档审计门禁。
3. **P2（数据驱动长效运营）**：建立基于受控错误统计的周期性复盘机制，根据实际接入模型与宿主反馈持续微调易错字段说明。
